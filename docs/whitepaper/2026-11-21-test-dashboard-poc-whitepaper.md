## 1. 요약

**질문.** 설계 문서 없이 코드 구조 정보(온톨로지)와 정적 분석 결과(bbtg 산출물)만 LLM에 주면, 쓸 만한 BDD E2E 테스트를 만들 수 있는가? 온톨로지를 주는 것이 주지 않는 것보다 나은가?

**실험 구성.** 생성 입력만 다른 세 arm(실험군)을 각 3회 생성하고, 같은 SUT에 실행해 커버리지로 비교했다.
- `base`: bbtg 산출물만 준다(대조군).
- `jqa`: bbtg 산출물에 jQAssistant가 소스에서 추출한 구조 그래프를 더한다.
- `owl`: bbtg 산출물에 jQA 그래프를 OWL/RDF로 변환하고 LLM이 의미를 보강한 도메인 온톨로지를 더한다.

**결과(평균, 범위는 3회의 최소–최대).**

| 지표 | base | jqa | owl | 사람이 쓴 블랙박스 IT(35개) |
|---|---|---|---|---|
| 시나리오 수 | 29.7 (28–31) | 39.0 (38–40) | 41.0 (39–43) | 35 TC |
| 컴파일 성공 | 100% | 100% | 100% | — |
| 통과율 | 61.6% (57.1–67.7) | 62.2% (55.3–75.0) | 57.0% (53.5–59.0) | 100% |
| API 엔드포인트 커버(17개 중) | 49.0% (6–12개) | 68.6% (11–12개) | 68.6% (11–12개) | — |
| 라인 커버(TC 귀속) | 14.7% | 17.8% | 18.0% | 41.5% |
| 분기 커버(TC 귀속) | 7.8% | 10.0% | 9.5% | 30.8% |
| 비즈니스 규칙 오라클(10개 중) | 0 | 0 | 0 | — |

**판정.** 파이프라인의 자동 판정은 "생성 가설 불성립, 온톨로지 효과 차이 불명확(탐색적 관찰)"이다.
- 생성 가설: 온톨로지 arm이 통과율 70% 이상, 엔드포인트 커버 80% 이상을 모두 넘어야 성립한다. 두 기준 모두 넘지 못했다.
- 효과: 온톨로지 arm의 범위가 대조군 범위와 겹치지 않아야 "효과 있음"이다. 세 지표(엔드포인트, 분기, 오라클) 모두 겹쳤다.

**관찰.**
- 온톨로지는 **폭(어떤 API가 있는지)** 을 넓히고 결과를 안정시켰다. 엔드포인트 커버의 범위가 base 6–12개에서 jqa·owl 11–12개로 좁아졌다.
- 온톨로지는 **깊이(비즈니스 규칙)** 에는 도움을 주지 못했다. 세 arm 모두 오라클 0/10이다.
- 원인은 대부분 **LLM 입력에 없던 정보**로 설명된다(4.4, 5장).
  - 비즈니스 규칙의 임계값(숙박 1–30박, 객실 100–499 등)은 **bbtg가 분기 조건식으로 얻었다.** 그러나 파이프라인이 "SUT 소스 원문 금지" 규칙을 엄격히 해석해 번들에서 지웠다. 오라클 10개 중 7개는 조건식에 임계값까지 있었다.
  - jQA 그래프의 요청 DTO에 필드가 0개로 추출됐다.
  - 그 결과 예약 생성 API(`POST /api/reservations`)는 9개 generation 모두에서 핸들러까지 도달하지 못했다.

**후속 실험(9장): LLM 없이 결정적 값만으로 만들면?** bbtg 조건식과 보강한 jQA 그래프(DTO 필드, enum, 상수, 예외 핸들러 상태)만으로 규칙에 따라 케이스를 펼치는 `det` arm을 만들어 같은 SUT에 실행했다.
- 규칙이 펼칠 수 있는 칸(슬롯)은 130개다. 생성 80, 생성 불가 50(사유별 집계)이다. 생성 개수는 프롬프트 예산이 아니라 입력에서 계산된 값이다.
- 80개 중 73개가 기대 상태코드 그대로 통과했다(91.3%). 오라클 9/10, 엔드포인트 14/17, 분기 커버 37.2%(사람이 쓴 블랙박스 IT 30.8%보다 높음), boarding 범위 라인 73.4%·분기 63.6%다.
- 단, det는 LLM arm이 받지 못한 조건식을 읽는다. 그래서 이 차이는 "생성 방식"보다 "입력 정보"의 차이로 읽어야 한다(9.5).

## 3. 결정적 작업과 LLM 작업의 경계

이 장이 이 문서의 핵심이다. "결정적"은 **같은 입력이면 같은 출력이 나온다**는 뜻이다. "LLM 생성"은 같은 입력이라도 출력이 달라질 수 있고, 출력에 모델의 해석(의미 부여)이 들어간다는 뜻이다.

### 3.1 세 종류의 주체

| 주체 | 성격 | 예 |
|---|---|---|
| 코드·도구 (결정적) | 같은 입력 → 같은 출력. 결과를 다시 계산해 검증할 수 있다. | jQAssistant, JaCoCo/pjacoco, bbtg 분석 스킬, Cucumber, SonarQube, `td` 패키지 |
| LLM (비결정적, 의미 부여) | 같은 입력에서도 반복마다 결과가 다르다. 이름·관계·의도를 해석해 붙인다. | OWL 의미 보강(S05), BDD 시나리오·glue 생성(S06) |
| 사람 (판단 기준 설정) | 평가 기준과 정답을 정한다. 생성 입력에는 들어가지 않는다. | 오라클 규칙 10개, 기대 엔드포인트 17개, 판정 임계값, 프롬프트 |

### 3.2 단계별 분류

| 단계 | 결정적 부분 | LLM 부분 | 사람이 정한 부분 |
|---|---|---|---|
| S00 | 버전·커밋·플래그 검사 | claude 호출 1회("reply with OK"): 격리 플래그가 동작하는지만 본다. 출력은 쓰지 않는다. | `tools.pin.yaml`(도구 SHA 고정) |
| S01 | IT 실행, pjacoco TC별 수집, 귀속 계산 | 없음 | IT 35개(SUT 저장소에 원래 있던 것), 귀속 불가 8개 목록 |
| S02 | bbtg 7개 스킬(tree-sitter 기반 정적 분석, LLM 호출 없음), 정제 | 없음 | 정제 규칙(어떤 필드를 지울지) |
| S03 | jQA 스캔과 Cypher 질의 | 없음 | 질의 정의(어떤 노드·관계를 뽑을지) |
| S04 | HTML 렌더링 | 없음 | — |
| S05 | OWL 골격(jQA 노드→클래스·속성), SHACL 검증, 병합 규칙 | 설명문(`rdfs:comment`) 55개, 관계 이름 5개, 제약(`owl:Restriction`) 15개, 상·하위 분류 | 보강 프롬프트, 허용 타입 규칙 |
| S06 | 번들 구성·검사·서명, 입력 해시, 스키마 검증, 최대 2회 수리 루프 제어, 스냅샷 저장 | feature 파일 구성, 시나리오 선택과 수, 단계 문장, 요청 본문 값, 기대 상태 코드, Java glue 코드 전체 | 생성·수리 프롬프트, 시나리오 예산(25–45개), `CONTRACT.md`(하네스 계약) |
| S07 | 컴파일, Cucumber 실행, 시나리오별 커버리지 | 없음(실행만) | — |
| S08–S11 | 커버리지·핫스팟·TIA·Sonar 계산 | 없음 | 핫스팟 설정, TIA 커밋 범위 |
| S12 | 지표 집계, 범위 겹침 판정 | 없음 | 임계값(컴파일 ≥90%, undefined ≤10%, 통과 ≥70%, 엔드포인트 ≥80%), 오라클 10개, 판정 문구 |

### 3.3 LLM이 만든 것의 구체적 내용

**S05 OWL 보강.** 골격은 jQA 그래프에서 기계적으로 만든다(Entity 7, DTO 4, Field 32, Endpoint 17). LLM이 이 골격 위에 얹은 것은 다음과 같다.
- **설명문 55개.** 예: `Reservation_nights` → "Number of nights the pet is booked to stay." 필드 이름을 사람 말로 풀어 쓴 것이다. 값의 범위(1–30박)는 들어 있지 않다. 그 정보가 입력에 없었기 때문이다.
- **관계 이름.** 예: `owns pet`, `pet visit`, `veterinarian specialty`.
- **제약 15개.** 예: `Pet_name` 최소 1개, `Pet_type` 최대 1개. 모두 개수(카디널리티) 제약이고, 값의 범위 제약은 없다.

**S06 BDD 생성.** generation 하나당 feature 파일 5–10개와 같은 수의 step 클래스, 그리고 `glue/support/` 도우미를 만든다. LLM이 정한 것은 다음과 같다.
- **무엇을 테스트할지.** 어떤 엔드포인트를 몇 번, 어떤 입력 변형으로 부를지.
- **요청 본문의 필드와 값.** 예: 예약 요청에 `petName`, `ownerEmail`, `nights=3`, `animalCount=1`, `roomNumber`(1–10 무작위), `checkInDate`(7–306일 뒤)를 넣었다.
- **기대 결과.** 예: "빈 본문이면 400".
- **시나리오 이름과 묶음.** 예: `reservation_validation.feature`.

### 3.4 결정성을 지키는 장치

LLM 출력 자체는 비결정적이다. 파이프라인은 LLM 출력을 **입력 해시로 고정한 스냅샷**으로 다뤄서, 같은 run을 다시 돌리면 같은 결과가 나오게 했다.

| 장치 | 내용 |
|---|---|
| 입력 키 | 번들 해시 + 프롬프트 해시 + 모델 ID로 `genId`를 만든다(예: `jqa-3e687e21-r2`). 입력이 하나라도 바뀌면 키가 바뀐다. |
| 스냅샷 재사용 | 키가 같은 완성 스냅샷(`_COMPLETE` 표식)이 있으면 claude를 부르지 않는다. 기준 run과 두 번째 run은 claude를 0회 호출했고, 두 run의 비교 지표는 같다. |
| 반복(rep) | 같은 입력으로 r1–r3을 따로 생성한다. LLM의 변동 폭을 측정하려는 것이다. |
| 격리된 호출 | `--tools ""`, 빈 MCP 설정, 설정 파일 무시, 고정 시스템 프롬프트, 임시 작업 디렉터리. LLM은 파일 시스템과 웹에 접근할 수 없고, 번들로 받은 텍스트만 본다. |
| 출력 검증 | 출력 JSON 스키마, 파일 경로 규칙, 컴파일 가능성. 실패하면 최대 2회 수리를 요청하고, 그래도 실패하면 그 generation을 실패로 기록한다. |

같은 입력에서 LLM이 얼마나 다르게 만드는지는 rep 사이 차이로 드러난다. 같은 base 입력의 r1–r3이 엔드포인트를 각각 12개, 6개, 7개 커버했다.

### 3.5 메타 수준: 파이프라인 코드 자체도 LLM이 작성했다

이 PoC의 코드·테스트·문서는 Claude Code 에이전트들이 작성했다. 구현 에이전트가 Task별로 구현하고, 리뷰 에이전트가 스펙 준수와 품질을 검토했으며, 사람은 결정을 내렸다. **작성 시점에는 LLM이 개입했지만, 실행 시점에는 코드가 결정적으로 동작한다.** 둘을 구분해야 한다.

- 실행 시점의 결정성은 수용 테스트 702개와 두 run의 동일한 지표로 확인했다.
- 작성 시점 LLM의 오류는 리뷰 단계에서 잡혔다. 예:
  - 홈 KPI 값을 어떤 단계도 쓰지 않던 결함을 시각 확인에서 발견했다.
  - 두 번째 Ctrl-C가 정리 명령을 죽이는 결함을 브랜치 전체 리뷰에서 실험으로 재현했다.
  - 게시물의 임시 경로 노출을 리뷰에서 발견했다.

### 4.3 LLM이 받은 정보의 성격

`ReservationService.create`의 테스트 계획 13건을 예로 들면 LLM이 받은 것은 다음과 같다.

```
{'branch_value': '400', 'expected_code': 400, 'expected_exception': 'ReservationValidationException',
 'id': 'errorPath_code400', 'param': '(from scenarios)', 'prefix': 'errorPath', ...}   × 8건
{'branch_value': '409', 'expected_code': 409, 'expected_exception': 'ReservationConflictException', ...}
{'branch_value': 'WELCOME10', 'id': 'happyPath_req_WELCOME10', ...}
```

즉 LLM은 "예약 생성에는 400을 내는 오류 경로가 8개, 409를 내는 경로가 1개 있다"는 **개수와 결과**는 알았다. 그러나 **어떤 조건에서** 400이 나는지(숙박 일수, 객실 번호 범위, 동물 수, 날짜, 보증금, 등급)는 몰랐다. bbtg는 이 조건을 얻었지만, 파이프라인의 정제 단계(S02)가 번들에 넣기 전에 지웠다. 자세한 내용은 4.4에 있다.

### 4.4 bbtg가 얻은 정보와 파이프라인이 지운 정보

**결론: bbtg는 조건식을 얻었다. 파이프라인이 활용하지 않기로 하고 지웠다.**

bbtg의 원본 출력(`work/runs/<runId>/S02/bbtg/raw/stdout/plan-tests-ReservationService.*.json`, 로컬 전용이며 게시하지 않음)에는 각 테스트 계획마다 `condition` 필드가 있다. 이 필드는 서비스 코드의 분기 조건식을 그대로 옮긴 것이다. `key-params/ReservationService_create.json`에도 같은 조건식이 `BRANCH_CONDITION` 근거로 들어 있다. 오라클 10개와 비교하면 다음과 같다.

| 오라클 | bbtg 원본 `condition` | 번들(정제 후) |
|---|---|---|
| ORC-02 숙박 1–30박 | `req.nights() < 1 \|\| req.nights() > 30` | `branch_value: "400"`만 남음 |
| ORC-03 객실 100–499 | `req.roomNumber() < 100 \|\| req.roomNumber() > 499` | 같음 |
| ORC-04 동물 1–4마리 | `req.animalCount() < 1 \|\| req.animalCount() > 4` | 같음 |
| ORC-05 도착일은 오늘 이후 | `req.checkInDate() == null \|\| !req.checkInDate().isAfter(LocalDate.now())` | 같음 |
| ORC-07 보증금 | `req.depositAmount() * 1.1 < req.nights() * req.priceTier().getNightlyRate()` | 같음 |
| ORC-08 VIP 포인트 500 | `req.priceTier() == PriceTier.VIP && req.loyaltyPoints() < 500` | 같음 |
| ORC-01 객실당 확정 2건 | `repository.countByRoomNumberAndStatus(...) >= ROOM_CAPACITY` | `branch_value: "409"`만 남음 |
| ORC-06 48시간 이내 삭제 불가 | `checkIn.isBefore(LocalDateTime.now().plusHours(48))` | 같음 |
| ORC-09 도착일 시작 후 수정 불가 | `!LocalDate.now().isBefore(existing.getCheckInDate())` | 같음 |
| ORC-10 상태 전이 규칙 | `... !existing.getStatus().canTransitionTo(req.status())` | 같음 |

- **조건식에 값이 그대로 있는 것은 7개다.** ORC-02, 03, 04, 05, 06, 08, 09는 임계값까지 조건식에 들어 있다.
- **ORC-01, 07, 10은 조건식만으로는 부족하다.** ORC-01의 `ROOM_CAPACITY` 값(2), ORC-07의 등급별 1박 요금, ORC-10의 허용 전이 그래프는 다른 클래스(상수, `PriceTier`, `ReservationStatus`)에 있다. 이 셋은 조건식이 있어도 추가 정보가 필요하다.
- **비교 근거:** bbtg 원본에는 `499`, `48`, `VIP`, `ROOM_CAPACITY`, `canTransitionTo`가 있다. base 번들에는 이 문자열이 하나도 없다(`grep`으로 확인).

**지운 이유.** 설계 문서의 생성 가설은 "온톨로지와 bbtg 산출물만으로(설계 문서, **SUT 소스 원문**, 사람이 쓴 기존 테스트 원문 없이)"다(설계 §1, 위협 A1).
- 구현 중(Task 16) 진행 관리 에이전트가 이 문구를 해석해 판정했다. 판정 내용은 "조건식은 소스 코드의 식을 그대로 옮긴 원문이므로 금지한다. 식별자(필드 이름, 파라미터 이름)는 허용한다"였다.
- 그 결과 `plan-tests`의 `condition` 38건, `expected` 38건, `description` 20건이 지워졌다. 같은 판정으로 `derive-test-data`의 `where_clause`·`formula`·SQL 문, `inspect-auth`의 분기 원문도 지워졌다(`manifest.json`의 `removedCounts`, `forbiddenDeclared`).
- 판정 기록(진행 기록, Task 16)에는 "base arm이 규칙 정보를 덜 받는 비용이 있다"는 점이 함께 적혀 있다.

**이 판정의 의미.** 사용자가 처음 정한 조건은 "온톨로지와 bbtg 산출물만, 설계 문서 없이, 기존 IT 원문 없이"였다. "SUT 소스 원문 금지"는 설계 문서를 쓰면서 추가된 문구다. 조건식을 원문으로 볼지는 해석의 문제였고, 이번 실험은 가장 엄격한 해석을 택했다. 그 결과 다음 두 가지가 결과에 섞였다.
1. **오라클 0/10의 큰 원인은 온톨로지의 한계가 아니라 정제 판정일 가능성이 높다(추정).** bbtg는 규칙 10개 중 7개의 임계값을 이미 갖고 있었다.
2. **이번 실험은 "bbtg 산출물을 활용하면 E2E를 만들 수 있는가"를 온전히 측정하지 못했다.** bbtg의 핵심 산출물인 분기 조건을 뺀 상태에서 측정했다.

**bbtg의 테스트 코드 생성 단계는 쓰지 않았다.** bbtg에는 테스트 코드를 직접 만드는 단계(`generate-tests`, 테스트 코드 + SQL + WireMock 스텁)도 있다. 이번 파이프라인은 분석 스킬 7개(`plan-tests` 포함)만 실행했다. 블랙박스 테스트는 bbtg로 다시 만들지 않고 SUT에 원래 있던 IT를 쓰기로 했기 때문이다(사용자 결정). 즉 bbtg의 테스트 계획 38건은 만들어졌지만, 그 계획을 테스트 코드로 바꾸는 일은 bbtg가 아니라 S06의 LLM이 정제된 계획을 받아서 했다.

### 5.2 효과가 난 이유: 목록(inventory) 정보

jQA 그래프는 엔드포인트 34개(HTML 뷰용 MVC 컨트롤러 포함, REST만 세면 17개)를 HTTP 메서드, 경로, 핸들러와 함께 명시적으로 준다. base 번들에서는 엔드포인트 정보가 의존 관계와 테스트 계획 안에 흩어져 있다. 엔드포인트 목록을 직접 받으면 LLM이 "모든 엔드포인트 그룹에 성공 경로 시나리오 하나 이상"이라는 프롬프트 지시를 더 안정적으로 지킬 수 있었다. 이 연결은 추정이다. 측정된 사실은 엔드포인트 커버의 최솟값이 6개에서 11개로 오르고 범위가 좁아졌다는 것이다.

### 5.3 효과가 나지 않은 이유: 의미(semantics) 정보의 부재

**원인 1: 요청 DTO의 필드가 추출되지 않았다(결정적 추출 단계의 공백).**
jQA 그래프의 DTO 노드 4개(`CreateReservationRequest` 포함)는 `hasField` 관계가 **0개**다. Field 노드 36개는 모두 Entity의 필드다.

(2026-11-22 정정) 처음에는 jQA가 Java record의 구성 요소를 필드로 잡지 못한 것으로 추정했다. 확인해 보니 **jQA 저장소에는 필드가 모두 있었다**(`CreateReservationRequest` 10, `UpdateReservationRequest` 2, `ReservationResponse` 12, `LoginRequest` 2). 원인은 이 파이프라인의 질의다. `dtos.cypher`는 DTO 타입 이름과 엔드포인트 연결만 반환하고, 필드는 `@Entity` 범위로 묶인 `entities.cypher`에서만 꺼냈다. 같은 저장소에는 enum 상수, `ROOM_CAPACITY=2` 같은 정적 상수값, 핸들러→서비스 호출, 예외 핸들러가 호출하는 `ResponseEntity` 빌더(→ 검증 예외는 422)도 있었다. 9장의 det arm은 이 정보를 별도 파일(`ontology-jqa-ext.json`)로 꺼내 썼다. 기존 arm의 입력은 바꾸지 않았다.

실제 요청 DTO는 다음과 같다.

```java
public record CreateReservationRequest(String petName, String ownerEmail, String promoCode, int roomNumber,
    int nights, int animalCount, int loyaltyPoints, PriceTier priceTier, double depositAmount,
    LocalDate checkInDate)
```

LLM이 만든 요청 본문에는 이 10개 중 6개(`petName`, `ownerEmail`, `nights`, `animalCount`, `roomNumber`, `checkInDate`)만 있다. `priceTier`, `depositAmount`, `loyaltyPoints`, `promoCode`는 없다.

다만 필드 이름의 힌트가 전혀 없었던 것은 아니다. 예약 테이블의 컬럼 목록(`derive-test-data.json`의 `java_field: depositAmount`, `priceTier` 등)과 jQA의 `Reservation` 엔티티 필드는 번들에 있었다. 그러니 "요청 DTO 필드가 0개로 추출됐다"는 공백과 "LLM이 엔티티 필드 힌트를 요청 본문에 다 쓰지 않았다"는 생성 쪽 문제가 함께 작용했다.

**원인 2: 핸들러에 도달하지 못했다.**
`POST /api/reservations`는 **9개 generation 모두에서** 핸들러 메서드의 라인이 하나도 실행되지 않았다. 응답은 `{"status":400,"error":"Bad Request","path":"/api/reservations"}`였다. 서비스 검증 예외의 응답이 아니라 요청 본문 변환 단계의 400으로 보인다. 원시 타입(`int`, `double`) 필드가 빠진 record를 역직렬화하다 실패한 것으로 추정한다. 이 가설은 따로 재현해 확인하지는 않았다. 예약이 만들어지지 않으니 그 뒤 흐름도 막혔다.

| 엔드포인트 | 9개 generation 중 미커버 횟수 |
|---|---|
| `POST /api/reservations` | 9 |
| `GET /api/reservations/{id}` | 9 |
| `POST /api/pets` | 9 |
| `PUT /api/pets/{petId}` | 8 |
| `GET /api/reservations` | 7 |
| `POST /api/auth/validate` | 5 |
| 그 밖의 5개 | 1–3 |

**원인 3: 비즈니스 규칙의 값이 어떤 입력에도 없다.**
오라클 10개는 모두 `ReservationService` 안의 규칙이다. 예: 숙박은 1–30박만 허용, 객실 번호는 100–499, 동물은 1–4마리, 도착일은 오늘 이후, 최상위 가격 등급은 포인트 500 이상 필요, 도착 48시간 이내에는 삭제 불가. 이 값들은 소스 코드의 조건식에만 있다.
- jQA 그래프는 구조(클래스, 필드 이름, 의존)만 담는다.
- OWL 보강은 그 구조를 사람 말로 풀었을 뿐 값을 만들어내지 않았다. 설명문에 "Number of nights the pet is booked to stay"는 있지만 "1–30"은 없다.
- bbtg는 이 값들을 조건식으로 얻었지만, 오염 방지 규칙에 따라 정제 단계에서 지웠다(4.4).

그래서 LLM이 할 수 있었던 것은 "숙박 일수 -1이면 400" 같은 상식적인 추측뿐이었다. LLM이 고른 객실 번호 1–10은 실제 허용 범위(100–499) 밖이다.

**원인 4: OWL은 독립 정보원이 아니다.**
OWL 골격은 jQA 그래프에서 파생하고, LLM 보강은 이름을 풀어 쓴 것이다. 그래서 `owl` arm은 `jqa` arm과 같은 정보를 다른 형식으로 받은 셈이다. 두 arm의 엔드포인트 커버가 정확히 같고(11·12·12) 라인 커버 차이가 0.2%p인 것과 일치한다. 그런데 owl 번들(33.5 KB)이 jqa 번들(53.1 KB)보다 작은데도 토큰은 owl이 1.5% 많다. 이유는 확인하지 못했다.

### 5.4 거짓 통과(false pass)에 대한 주의

`reservation_validation.feature`의 "숙박 일수가 음수면 400" 같은 시나리오는 **통과**로 기록됐다. 그러나 이 400은 서비스 규칙이 아니라 요청 본문 변환 실패에서 나왔을 가능성이 높다(5.3 원인 2). 상태 코드만 확인하는 단언은 "왜 400인가"를 구별하지 못한다. 그래서 통과율보다 **오라클 커버**(규칙 라인의 분기 실행 여부)가 더 정확한 깊이 지표다.

## 6. 가능한 모든 케이스를 생성할 수 있는가

### 6.1 짧은 답

**아니다.** 이유는 세 가지다.
1. **입력 공간이 무한하다.** 요청 필드의 값 조합(문자열, 날짜, 숫자)은 셀 수 없다. "모든 케이스"는 유한한 목표로 정의해야만 측정할 수 있다.

## 7. 한계와 해석상 주의

1. **표본이 작다.** arm당 3회다. 평균과 범위는 탐색적 관찰이고 통계적 유의성을 주장하지 않는다. 판정 규칙(범위가 겹치지 않아야 효과 있음)은 보수적이다.
2. **SUT가 하나다.** petclinic fork 하나에서 얻은 결과다. 엔드포인트 17개 규모의 작은 서비스다.
3. **오라클은 사람이 정했다.** 목록에 없는 규칙의 커버는 측정하지 않는다. 오라클 작성자가 생성 입력을 설계한 사람과 같다.
4. **TC 귀속 한계.** pjacoco는 `HttpServlet#service` 단위로 귀속한다. 보안 필터 체인에서 끝나는 요청의 커버리지는 TC에 귀속되지 않고 집계에만 남는다. 블랙박스 IT 8개가 여기에 해당한다.
5. **사전 지식 오염 가능성.** 모델이 원본 spring-petclinic을 학습했을 수 있다. 그래서 fork 고유 `boarding` 패키지를 따로 집계한다. 집중 범위 라인 커버는 base 13.9%, jqa 13.9%, owl 9.2%다.
6. **오염 방지 규칙이 결과에 크게 영향을 줬다.** bbtg는 규칙 10개 중 7개의 임계값을 조건식으로 얻었지만, "SUT 소스 원문 금지"를 엄격히 해석해 번들에서 지웠다(4.4). 그래서 이번 결과는 "온톨로지가 깊이를 못 준다"와 "정제 판정이 깊이 정보를 막았다"를 구분하지 못한다. 조건식을 허용하는 arm을 추가하면 이 판정의 영향을 따로 측정할 수 있다.
7. **결정적 추출의 공백.** DTO 필드가 0개로 추출된 것은 LLM 문제가 아니라 jQA 질의 단계의 문제다. 다만 엔티티 필드와 테이블 컬럼 이름은 번들에 있었으므로, 요청 본문이 불완전했던 데에는 LLM의 활용 부족도 함께 작용했다(5.3).

## 8. 다음 실험을 위한 제안

효과가 클 것으로 보는 순서로 적었다. 순서 판단은 추정이다.

0. **bbtg 조건식 허용 arm 추가(가장 먼저).** 정제 판정을 "식별자와 비교 상수는 허용, 메서드 호출식은 구조화한 형태로만 허용"처럼 완화한 번들로 같은 실험을 다시 한다. bbtg가 이미 얻은 임계값 7개를 쓸 수 있으므로, 오라클 0/10이 정제 판정 때문인지 바로 확인할 수 있다. 원문 금지의 취지(설계 의도·사람 테스트의 노하우 유입 차단)를 지키려면, 원문 문자열 대신 `{field: nights, min: 1, max: 30, onViolation: 400}` 같은 구조화된 제약으로 바꿔 넣는 방식이 있다.
1. **요청 DTO 필드 추출 보강(결정적).** jQA 질의에 record 구성 요소와 타입을 추가한다. `POST /api/reservations` 핸들러 도달이 첫 번째 관문이다. → det arm에서 보강 질의로 구현했다(9장). 기존 arm에는 아직 넣지 않았다.
2. **제약값을 담은 온톨로지(결정적).** Bean Validation 어노테이션, 서비스의 상수 비교식, 열거형 값을 추출해 OWL 데이터 속성 제약(`xsd:minInclusive` 등)으로 넣는다. 이렇게 하면 OWL이 jQA 그래프를 다시 쓴 것이 아니라 독립 정보를 갖게 된다.
3. **조건식 허용 arm 추가.** bbtg 조건식을 남긴 번들을 네 번째 arm으로 두면, 오염 방지 규칙의 비용을 측정할 수 있다.
4. **단언 강화.** 상태 코드만 확인하지 않고 응답 본문의 오류 코드나 메시지 종류를 확인하게 한다. 거짓 통과(5.4)를 줄인다.
5. **목표 공간을 결정적으로 정의.** "엔드포인트 × 결과 유형"을 17개 엔드포인트 전체로 계산해, 시나리오 수 대신 칸 커버율을 생성 지표로 쓴다.
6. **반복 수 확대.** generation 1건은 약 $0.5–1.1(평균 $0.75)다. arm당 10회(3개 arm, 총 30건)로 늘리면, 이미 있는 9건을 빼고 21건에 약 $16가 더 든다.

## 9. 결정적 생성 실험(det arm, 2026-11-22)

### 9.1 질문과 방법

**질문.** bbtg와 온톨로지가 결정적으로 준 값만으로, 생성 개수를 제한하지 않으면 테스트 케이스를 최대 몇 개 만들 수 있는가? 그 케이스는 실제로 통과하고 커버리지를 올리는가? LLM으로 개수를 늘리는 것은 목적이 아니다.

**방법.** 네 번째 arm `det`를 추가했다. 생성 경로에서 LLM을 한 번도 부르지 않는다.
- 입력(닫힌 목록)은 세 가지다.
  - 현재 run의 bbtg 원본: `plan-tests` 조건식과 기대 코드, `key-params`, `inspect-auth` 필수 헤더
  - jQA 그래프와 보강 파일 `ontology-jqa-ext.json`: DTO 필드, enum 상수, 정적 상수값, 핸들러→서비스 호출, 핸들러 파라미터, 예외별 응답 상태
  - 하네스 설정: 로그인 엔드포인트, 비인증 상태 403, SUT 타임존
- SUT 소스 원문, 사람이 쓴 IT, 설계 문서, `oracle.yaml`은 읽지 않는다.
- 생성기(`site-gen/td/detgen/`)는 Java 문법 수준 규칙만 안다.
  - 조건식을 원자식으로 나누고 연산자별 경계값을 만든다. 예: `f < a` → 위반 a−1, 유효 a.
  - 위반 케이스는 원자식 하나만 깨고 나머지 필드는 모든 제약을 만족하는 기준값으로 채운다.
  - 기대 상태는 그래프에서 도출한 예외 상태를 먼저 쓰고, 없을 때만 bbtg 코드를 쓴다.
- 생성기 소스에 SUT 고유 이름(필드명, 클래스명, enum, 경로, 임계값)을 쓰지 않는다. 이름과 임계값을 모두 바꾼 변조 입력을 넣으면 출력에 원래 이름이 하나도 남지 않는다. 이를 테스트로 확인했다.
- 결과는 Gherkin과, 저장소에 고정된 glue 한 벌로 기존 S07/S08/S12를 거친다.

**결정적/LLM 경계.** det의 케이스 목록, 값, 기대 상태는 모두 코드가 정한다. 생성기와 glue 코드 자체는 이번 세션에서 LLM 에이전트가 한 번 작성했지만, 실행마다 다시 생성되지는 않는다(3.5와 같은 메타 수준). 같은 입력을 두 번 생성하면 바이트 단위로 같다. run1과 run2의 det generation은 같은 genId(`det-f5ea78f7-r1`)였고 결과도 같았다. 최종 리뷰 수정(타임존 전달, 키에 생성기 소스 체크섬 포함) 뒤의 run3에서는 genId가 `det-da70932c-r1`로 바뀌었고, 수치는 run2와 모두 같았다.

### 9.5 해석과 주의

1. **입력 체제가 다르다.**
   - det는 LLM arm이 받지 못한 조건식과 보강 그래프를 읽는다. 그래서 위 표의 차이는 "LLM 대 결정적 생성"의 효과가 아니라 대부분 **정보의 차이**다.
   - 같은 정보를 LLM에 줬을 때의 결과는 측정하지 않았다(8장 0번 제안).
   - det는 비교 화면에서 참고 열로만 나오고, 사전 등록 판정(생성 가설·효과)에서는 빠진다.
2. **오라클 9/10은 "규칙 라인이 실행됐다"는 뜻이다.**
   - 이 지표는 커버리지 기반이다. 그래서 ORC-01, 10(정원, 상태 전이)처럼 케이스를 만들지 못한 규칙도, 다른 요청이 그 검사 라인을 지나가면 covered가 된다.
   - 규칙의 결과(409 등)를 단정한 케이스가 있는 것은 6개(9.2)다.
3. **라인 커버는 블랙박스보다 낮고 분기 커버는 높다.**
   - det는 boarding 규칙의 분기를 깊게 훑는다(boarding 분기 63.6%).
   - 반면 Owner/Pet/Vet는 그래프 전용 규칙(인증, 없는 id, 본문 없는 GET)만 만들어 정상 흐름 라인을 덜 지난다.
4. **"모든 케이스"가 아니다.**
   - 규칙 모수 130은 이 문법 목록과 이 입력에서 나오는 칸이다. 이론 상한 46,689와는 다르다.
   - 단일 결함 원칙이라 필드 조합 케이스는 만들지 않는다.
   - 동시 요청 경쟁(정원 검사 후 저장 사이)은 범위 밖으로 기록만 했다.
5. **문법 과적합 가능성.**
   - 값 하드코딩은 변조 입력 테스트로 막았다.
   - 그러나 지원하는 조건식 모양은 이 SUT에서 나온 것들이다. 다른 SUT에서는 `unparsed`가 늘 수 있다.

### 9.6 결론

- **질문의 답은 "그렇다, 다만 정보가 있는 곳까지"다.**
  - bbtg와 jQA가 준 결정적 값만으로 LLM arm의 약 2배인 80개를 만들었고, 91%가 기대 상태 그대로 통과했다. 생성 개수는 예산이 아니라 입력에서 계산됐다.
  - 생성 불가 50칸은 사유별로 무엇이 빠졌는지를 알려 준다. 사유는 상태 전이표, 그래프에 없는 값, 컨트롤러 검증, 자격 증명 등이다.
- **다음에 손댈 곳은 생성 불가 사유 표의 위쪽이다.**
  - 상태 전이와 초기 상태(14칸)는 enum 메서드 분석이나 bbtg의 상태 분석을 보강해야 열린다.
  - 컨트롤러 검증(실패 4건)은 bbtg 계획 대상을 컨트롤러까지 넓히면 들어온다. 이번에 범위로 정한 (a)(기존 bbtg 결과만 사용)를 넘는 작업이다.
- **같은 정보를 LLM arm에도 주는 실험**(8장 0번)을 해야 "생성 방식"의 효과를 분리할 수 있다.


### 9.7 pairwise 추가 결과

**질문.** 9장의 det는 위반을 한 필드씩만 깨는 단일 결함 방식이라, 유효한 값끼리의 조합은 거의 시험하지 않았다. 같은 결정적 입력에서 유효 값 조합을 PICT(Microsoft, v3.7.4 고정 커밋을 소스에서 빌드)로 2-way·3-way로 펼치면 케이스가 얼마나 늘고 커버리지가 오르는가?

**방법.**
- 필드별 유효 후보 값은 기존 경로에서만 뽑는다: baseline, 오류 조건의 유효 경계값, 여러 원자식이 묶인 오류 조건의 위반값(다른 원자식이 거짓이면 유효), enum 상수, 분기 진입 값.
- 여러 원자식이 모두 참이 되는 조합(예: 등급 VIP ∧ 포인트 499)은 PICT 제약으로 배제한다. 위반 클래스끼리는 조합하지 않는다(첫 위반에서 거부되면 둘째 위반이 가려지는 마스킹 때문).
- 상태 전이 enum, count 인자, 관계식 종속 필드, 저장 상태 필드는 조합에서 빼고 기준값으로 고정한다.
- PICT에는 필드명·값 대신 `p<i>`/`v<j>` 라벨만 넘기고, 같은 모델이면 같은 행이 나온다(`/r` 미사용). 테스트가 PICT 출력이 아니라 케이스 값에서 "배제를 만족하는 모든 조합이 실제로 들어 있는가"를 다시 센다.

**결과(같은 SUT 커밋 b6f9393).**

| 항목 | det(run3, 9장) | det + 2-way | det + 3-way |
|---|---|---|---|
| run | 20261121-201248Z-…-9d5ee1f4 | 20261122-075628Z-…-06cbd507 | 20261122-083102Z-…-dac4592a |
| 케이스 | 80 | 88(pairwise 8개) | 98(pairwise 18개) |
| pairwise 케이스 통과 | – | 8/8 | 3-way 18개 중 18개 통과 |
| 실현 가능 조합 덮음 | – | 2-way 69/69 | 3-way 192/192 |
| strict 통과 | 73/80 | 81/88 | 91/98 |
| 라인(TC 귀속) | 31.06% | 31.06% | 31.06% |
| 브랜치(TC 귀속) | 37.15% | 37.15% | 37.15% |

- 조합이 늘어난 곳은 POST /api/reservations 하나다. 다른 엔드포인트는 조합할 필드가 2개 미만이었다(상태 전이·count·관계식 필드가 고정됨).
- 커버리지 비교 조건(SUT 커밋, jacoco 도구 고정값)이 같아 비교 가능했고, 라인·브랜치 차이는 0.00%p다.
- pairwise 케이스 중 관계식 상대편 필드(박 수·등급)가 기준값이 아닌 케이스는 2-way 6개, 3-way 15개이며 모두 통과했다(보증금 극단값 가정이 유지됨).

**해석.**
- pairwise는 "모든 유효 조합 쌍이 적어도 한 번 실행된다"는 보장을 8개(3-way 18개) 케이스로 추가했고, 전부 통과했다. 유효 조합 사이의 상호작용 결함은 이 SUT에서 관측되지 않았다.
- 커버리지가 오르지 않은 이유는 이 SUT의 분기가 필드별 단일 조건(경계·null·enum)과 한 개의 2원자 조건으로 되어 있어, 단일 결함 케이스가 이미 각 분기의 양쪽을 지나기 때문이다. 유효 값 조합은 같은 경로를 다시 지난다. 이는 추측이 아니라 측정값(차이 0)이지만, 분기 구조가 다른 SUT에서는 달라질 수 있다.
- 따라서 이 SUT에서 pairwise의 가치는 커버리지가 아니라 조합 보장과 회귀 탐지(유효 조합이 2xx를 유지하는지)에 있다.
